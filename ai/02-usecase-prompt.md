Проаналізуй spec.md згенеруй два артефакти:
1. Use Case діаграму у синтаксисі PlantUML.
2. Матрицю трасування у вигляді Markdown-таблиці з колонками.

# Структуровані вимоги, сценарії використання і трасування.

## 1. Актори та головні цілі
1. **Користувач (User)** — Людина. 
   * *Ціль:* Шукати музику, слухати треки, збирати плейлісти та блокувати те, що не подобається.
2. **Преміум-користувач (Premium User)** — Людина (наслідує Користувача).
   * *Ціль:* Завантажувати треки на телефон, щоб слухати без інтернету і мати кращу якість звуку.
3. **Зовнішній Audio CDN** — Зовнішня система.
   * *Ціль:* Перевіряти права доступу і віддавати сам аудіофайл на пристрій.

## 2. Вимоги

### 2.1 EARS-вимоги
- **REQ-01:** WHEN користувач натискає "Play" на треку, система SHALL відправляє запит до External Audio CDN для початку стримінгу.
- **REQ-02:** WHEN користувач блокує артиста, система SHALL миттєво прибрає всі його треки з поточного плейліста.
- **REQ-03:** WHILE додаток працює без доступу до інтернету, система SHALL дозволяє відтворення тільки завантажених треків.
- **REQ-04:** WHERE плейліст містить більше ніж 50 треків, система SHALL вмикає підвантаження списку частинами.
- **REQ-05:** WHILE система у фоні оновлює метадані бази, система SHALL записує всі помилки у внутрішній лог.

### 2.2 User Stories
- **US-01:** Як Користувач, я хочу заблокувати конкретного артиста, щоб його пісні не псували мій настрій у рекомендаціях.
- **US-02:** Як Преміум-користувач, я хочу завантажити улюблений плейліст, щоб слухати його в метро без зв'язку.
- **US-03:** Як External Audio CDN, я хочу отримувати валідні токени від бекенду, щоб безпечно роздавати аудіо.

### 2.3 Сценарії
Scenario: SC-01. Блокування артиста
  Given я авторизований користувач
  And я знаходжуся на сторінці гурту "Artist X"
  When я натискаю кнопку "Заблокувати"
  Then система додає цього артиста до мого чорного списку
  And музика цього гурту зникає з моїх рекомендацій

Scenario: SC-02. Прослуховування треку через CDN
  Given я вибрав пісню "Track Y"
  When я натискаю на відтворення
  Then система просить токен у External Audio CDN
  And CDN починає передавати мені аудіопотік

Scenario: SC-03. Офлайн прослуховування
  Given у мене є статус Premium User
  And я вимкнув інтернет на телефоні
  When я запускаю завантажену пісню "Track Z"
  Then система грає трек із локальної пам'яті

  ## 3. Критерії прийняття
1. Use Case діаграма має містити щонайменше 2 типи акторів, включаючи одну зовнішню систему.
2. На діаграмі обов'язково мають бути використані зв'язки include, extend та узагальнення  для Premium User.
3. Матриця трасування має чітко показувати зв'язки "багато-до-багатьох" між EARS-вимогами та Use Cases.
4. У матриці трасування обов'язково має бути позначена щонайменше одна непокрита вимога.
5. Артефакт Use Case діаграми має генеруватися у форматі PlantUML.

## Відповідь ШІ
@startuml
left to right direction

actor "Користувач (User)" as User
actor "Преміум-користувач (Premium User)" as PremiumUser
actor "Зовнішній Audio CDN" as CDN << System >>

' Наслідування акторів
User <|-- PremiumUser

rectangle "Система стримінгу музики" {
  usecase "Відтворювати трек" as UC_PlayTrack
  usecase "Заблокувати артиста" as UC_BlockArtist
  usecase "Отримати токен аутентифікації" as UC_GetToken
  usecase "Підвантажувати плейліст частинами" as UC_Paginate
  usecase "Завантажити плейліст" as UC_Download
  usecase "Слухати в офлайн-режимі" as UC_OfflinePlay
}

' Зв'язки акторів із прецедентами
User --> UC_PlayTrack
User --> UC_BlockArtist

PremiumUser --> UC_Download

' Взаємодія з зовнішньою системою
CDN <-- UC_GetToken

' Включення (include)
UC_PlayTrack .> UC_GetToken : <<include>>

' Розширення (extend)
UC_Paginate .> UC_PlayTrack : <<extend>>\n(якщо > 50 треків)
UC_OfflinePlay .> UC_PlayTrack : <<extend>>\n(якщо відсутній інтернет)

@enduml

## Другий промпт
Перегенеруй PlantUML діаграму та Матрицю трасування з урахуванням виправлень:

1. US-01/SC-01 стосуються блокування артистів, а US-02/SC-03 — офлайн-режиму. Вони не мають стосунку до пагінації. Окремої User Story для пагінації немає, залиш у колонках User Story та Scenario  "-".

2. Виведи матрицю у формі Markdown-таблиці всередині блоку markdown . Зроби 5 колонок:
     | ID Вимоги (EARS) | User Story | Gherkin-сценарій | Use Case (Прецедент) | Статус покриття | Для REQ-01..REQ-04 у колонці "Статус покриття" вкажи "Покрито". Для REQ-05 у колонці "Статус покриття" вкажи "Не покрито (Out of scope / фоновий процес)", а в інших колонках вкажи "-".

3. Виведи PlantUML код всередині блоку plantuml. "Слухати в офлайн-режимі" має бути явно з'єднаний зв'язком з актором PremiumUser.
   - REQ-04 підвантаження частинами стосується плейлістів (>50 треків), а не відтворення треку. Додай  "Переглядати плейліст" та зроби "Підвантажувати плейліст частинами" його розширенням extend

### EARS-вимоги

 | ID | Шаблон EARS | Умова (WHEN / IF / WHILE / WHERE) | Реакція: система SHALL … |
| :--- | :--- | :--- | :--- |
| **REQ-01** | Подія (Event-driven) | **WHEN** авторизований користувач запускає відтворення треку, який не заблокований для нього | система **SHALL** почати передачу аудіопотоку (час старту — NFR-01) |
| **REQ-02** | Небажана ситуація (Unwanted behaviour) | **IF** джерело аудіо повернуло помилку або не відповіло протягом 5 секунд | **THEN** система **SHALL** показати користувачу повідомлення про помилку й не починати відтворення |
| **REQ-03** | Подія (Event-driven) | **WHEN** користувач блокує артиста | система **SHALL** зберегти блокування для цього користувача; виключити артиста з його рекомендацій; пропускати під час автовідтворення плейліста треки, одним з авторів яких є заблокований артист |
| **REQ-04** | Подія (Event-driven) | **WHEN** користувач блокує трек | система **SHALL** зберегти блокування; зробити трек невідтворюваним для цього користувача; залишити трек у плейлістах із позначкою «недоступний» (зв'язок плейліст–трек не видаляється); пропускати його під час автовідтворення |
| **REQ-05** | Подія (Event-driven) | **WHEN** користувач додає трек у «Вибране» | система **SHALL** створити зв'язок «користувач–трек (favorites)», якщо такого зв'язку ще немає |
| **REQ-06** | Подія (Event-driven) | **WHEN** користувач створює плейліст із непорожньою назвою | система **SHALL** створити `PLAYLIST` із `user_id` поточного користувача та `created_at` (timestamp, UTC), що дорівнює поточному моменту |
| **REQ-07** | Подія (Event-driven) | **WHEN** користувач відкриває плейліст, у якому понад 50 треків | система **SHALL** завантажувати список порціями по 50 треків |
| **REQ-08** | Подія (Event-driven) | **WHEN** користувач вводить пошуковий запит | система **SHALL** повернути збіги за назвою треку, назвою альбому та ім'ям виконавця, згруповані за типом сутності |
| **REQ-09** | Опційна функція (Optional feature) | **WHERE** у користувача активний статус Premium, **WHEN** він запускає завантаження плейліста | система **SHALL** зберегти в пам'яті пристрою аудіофайли всіх незаблокованих треків цього плейліста |
| **REQ-10** | Стан (State-driven) | **WHILE** пристрій не має доступу до інтернету | система **SHALL** дозволяти відтворення лише завантажених треків; для решти показувати повідомлення «Недоступно офлайн» |
| **REQ-11** | Подія (Event-driven) | **WHEN** Провайдер метаданих надсилає оновлення каталогу | система **SHALL** створити або оновити відповідні `ARTIST`, `ALBUM`, `TRACK` та їхні зв'язки (releases, authors, contains), зберігаючи наявні UUID |

  ## Критерії прийняття
1. Use Case діаграма має містити щонайменше 2 типи акторів, включаючи одну зовнішню систему.
2. На діаграмі обов'язково мають бути використані зв'язки include, extend та узагальнення  для Premium User.
3. Матриця трасування має чітко показувати зв'язки "багато-до-багатьох" між EARS-вимогами та Use Cases.
4. У матриці трасування обов'язково має бути позначена щонайменше одна непокрита вимога.
5. Артефакт Use Case діаграми має генеруватися у форматі PlantUML.
