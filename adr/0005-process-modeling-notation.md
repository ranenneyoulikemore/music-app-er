# [ADR-0005] Вибір нотації та форми моделювання бізнес-процесу відтворення треку (UC-02)

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-11-08
- **Оновлено:** 2026-11-14 (за AI-CHECK)
- **Контекст:** Необхідно обрати єдину декларативну форму для деталізації сценарію UC-02 ("Відтворення треку"), яка об'єднує успішне відтворення (`SC-01`), відмову через блокування (`REQ-03`, `REQ-04`) та помилку або таймаут очікування відповіді сховища (`SC-02`, `REQ-02`).

## Context and Problem Statement

Для виконання вимог потрібно описати один бізнес-процес однією формою без змішування нотацій. Модель повинна візуалізувати розподіл ролей (пули / swimlanes), розгалуження логіки (if/else), паралельне виконання завдань (fork/join) та асинхронний обмін повідомленнями з обробкою відсутності відповіді (таймаут 5 секунд).

Яку нотацію та інструмент обрати для опису бізнес-процесу, щоб забезпечити наочність при код-рев'ю на GitHub та узгодженість із попередніми моделями?

## Decision Drivers

- **Суть процесу:** це потік дій чотирьох учасників із розгалуженням за `isBlocked`, паралельними гілками метаданих і аудіопотоку та очікуванням події з таймером. Це елементи Activity-діаграми.
- **Розподіл відповідальності (Swimlanes):** Чітке розділення дій між актором та сервісами (`User`, `AppClient`, `AudioService`, `AudioStorageProvider`).
- **Підтримка паралелізму та подій:** Можливість явно показати Fork/Join та очікування події (таймер 5 с) без дедлоку на Join.
- **Візуалізація та рендеринг (NFR/DoD):** Нативний рендер у Markdown на GitHub без додаткових плагінів.
- **Узгодженість із Завданням 3:** Назви повідомлень збігаються з Sequence-діаграмами; паралельність і асинхронність відрізняються від них свідомо.

## Considered Options

1. **BPMN 2.0 XML** — галузевий стандарт моделювання процесів з багатою семантикою.
2. **Mermaid stateDiagram-v2** — моделювання переходів між станами системи або окремої сутності.
3. **Activity-діаграма у синтаксисі Mermaid Flowchart** — графічний опис потоку робіт із розділенням на пули через `subgraph`.

## Decision Outcome

Обрали **Опцію 3 (Activity-діаграма у Mermaid Flowchart)**: процес є потоком дій між учасниками, тобто саме те, що описує Activity-діаграма, а `stateDiagram-v2` описує стани однієї сутності.

Процес змодельовано в `doc/diagrams/uc-02-process-activity.md` з 4 пулами (`subgraph`), вузлами `Fork`/`Join`, вузлом очікування події (`WaitEvent`). Після помилки джерела або таймауту гілка очікування доходить до `Join`, далі розгалуження за результатом.

### Consequences

- **Good:** Нативний графічний рендер у GitHub PR без необхідності відкривати сторонні XML/файли зображень.
- **Good:** Зручний розподіл ролей за допомогою `subgraph`; пули збігаються з учасниками Sequence-діаграм Завдання 3, крім `BlockService` і `TrackRepository`, які показані кроками всередині `AudioService`.
- **Good:** Помилка джерела й таймаут змодельовано як події очікування: гілка доходить до `Join`, дедлоку немає, дострокового виходу з паралельної гілки немає.
- **Bad:** На відміну від BPMN 2.0 XML, синтаксис Mermaid Flowchart вимагає явного текстового позначення специфічних подій для забезпечення коректної семантики Activity-діаграми.
